## 1. Очередь воспроизведения (Playback Queue) — Приоритет #1

### Принятые решения (согласовано):
- [x] **Размер видимой очереди в UI**:
  - Ограничение в **30 треков** вперед, чтобы не перегружать интерфейс и память устройства.
- [x] **Перестройка очереди под контекст плейлиста**:
  - При нажатии на трек в плейлисте основная очередь **полностью перестраивается** под этот плейлист (играет выбранный трек, `Next` идет дальше по плейлисту, `Prev` — назад).
- [x] **Изолированная пользовательская очередь (Custom Queue / Play Next)**:
  - Если пользователь вручную добавил треки в очередь («Add to Queue» / «Play Next») из других мест:
    - Они ставятся в приоритетную очередь перед следующими треками плейлиста.
    - После того как эти изолированные треки отыграли, воспроизведение **бесшовно возвращается** к трекам из исходного плейлиста.
- [x] **Жест добавления в очередь (Swipe to Queue)**:
  - Свайп строки любого трека **вправо** (как в официальном приложении Spotify) добавляет песню в очередь с тактильным откликом / плашкой уведомления («Добавлено в очередь»).

### Ревью архитектуры (для справки):


Проверил android-app/ целиком: все 14 Kotlin-файлов, манифест, Gradle, нативный C-API, изменённый Rust-кор, ROADMAP.md и SWIFTIFY_DESKTOP_FEATURES.md. Debug-сборка компилируется (:app:compileDebugKotlin — BUILD SUCCESSFUL, 14 предупреждений), так что речь не о «не собирается», а о том, что получившийся продукт пока не является ни портом, ни приложением, готовым к использованию.
Короткий вердикт: это симпатичный, местами очень амбициозный прототип с хорошим визуальным чутьём, но архитектурно это один God-Activity, авторизация сломана по scope'ам и refresh-токену, воспроизведение не использует половину уже готового нативного API, а репозиторий и сборка не воспроизводимы. Ниже — по приоритетам, без смягчений.
0. Что сделано хорошо
Чтобы критика не выглядела тотальной:
- Приложение действительно компилируется и запускается, JNA-мост к libspotify_core.so работает.
- PKCE-авторизация через loopback 127.0.0.1:8898 — правильный подход для public client, и он совпадает с десктопом.
- Есть попытка сделать нормальный мобильный UI: динамическая палитра из обложки, расширенный плеер, очереди, поиск, экраны артиста/альбома/плейлиста.
- Нативная библиотека уже собрана с 16 KB LOAD-alignment — это правильно и пригодится при переходе на targetSdk 35+.
- ROADMAP.md и SWIFTIFY_DESKTOP_FEATURES.md показывают, что автор понимает масштаб задачи.
Дальше — проблемы.
1. P0 — блокеры, из-за которых приложение не работает как заявлено
1.1. OAuth-скоупы не дают доступа к Web API
MainActivity.kt:110:
private const val SCOPES = "streaming"
streaming — это скоуп Web Playback SDK, который здесь вообще не используется. При этом приложение дергает:
- /v1/me/player/recently-played (MainActivity.kt:397) → нужен user-read-recently-played;
- /v1/me/tracks/contains (ExpandedPlayer.kt:81) → нужен user-library-read;
- PUT /v1/me/tracks (ExpandedPlayer.kt:403) → нужен user-library-modify.
Все эти вызовы будут получать 403. То есть «недавно игравшее» на главной и лайки не работают в принципе, а ошибки проглатываются, и пользователь видит пустоту или «не лайкнут» вместо ошибки. Нужно как минимум:
streaming user-read-playback-state user-read-recently-played
user-library-read user-library-modify playlist-read-private
playlist-read-collaborative playlist-modify-private playlist-modify-public
user-follow-read
Плюс понять, что часть данных идёт через spclient в нативном коре (плейлисты, поиск), а часть — через Web API. Сейчас это две несогласованные ветки доступа.
1.2. Нет refresh-токена — через час всё отваливается
exchangeCodeForToken сохраняет только access_token и login blob. Refresh-токен Spotify не сохраняется и не используется. access token живёт ~3600 секунд, после чего:
- Web API-функции (recently played, лайки) умирают;
- приложение не умеет молча обновиться и не показывает, что токен истёк.
Для core-сессии есть connectStored(loginBlob), и она может жить дольше, но это не отменяет необходимость refresh-flow для Web API. Нужно хранить refresh_token, обновлять по 401, сериализовать обновление (Mutex), иметь состояние AuthState.Expired.
1.3. Состояние логина теряется при повороте экрана
codeVerifier и authServer — обычные поля Activity (MainActivity.kt:121-122), манифест не задаёт configChanges, ViewModel отсутствует. Сценарий: пользователь нажал «войти», ушёл в браузер, повернул телефон или система уничтожила Activity → codeVerifier потерян, ServerSocket закрыт, браузер получает connection refused или код приходит в мёртвый сервер. Логин приходится начинать заново.
Плюс:
- Нет параметра state — CSRF-защита OAuth отсутствует.
- ServerSocket не имеет таймаута: если пользователь закрыл браузер, authState навсегда остаётся Connecting, спиннер крутится вечно.
- Нет обработки занятого порта 8898 — ошибка только в лог.
- Нет onNewIntent для swiftify://login, хотя intent-filter в манифесте объявлен и не используется.
1.4. Токены лежат в открытом SharedPreferences, и они бэкапятся
PREFS_NAME = "swiftify_prefs", обычный getSharedPreferences, без шифрования. При этом:
- зависимость androidx.security:security-crypto подключена в build.gradle.kts, но нигде не используется;
- android:allowBackup="true" в манифесте без dataExtractionRules → login blob и access token могут уехать в Google-бэкап.
Для приложения, которое хранит фактически учётные данные Spotify, это недопустимо. Нужно EncryptedSharedPreferences (или DataStore + Keystore), allowBackup=false либо явные правила исключения, и удаление токенов при logout.
1.5. Настройки сохраняются, но не применяются при старте
SettingsScreen.kt пишет audio_quality_kbps и volume_norm в prefs и вызывает setStreamQuality/setVolumeNormalization только в момент клика. При следующем запуске:
- setStreamQuality не вызывается вообще;
- setVolumeNormalization не вызывается;
- setAudioCache не вызывается нигде;
- Spotify Connect при старте принудительно выключается (connectEnabled инициализируется false, MainActivity.kt:337 вызывает setSpotifyConnect(false)), хотя пользователь мог его включить.
То есть настройки — декоративные. Это классический признак отсутствия слоя инициализации/репозитория.
2. P1 — архитектура и воспроизведение
2.1. MainActivity.kt на 1685 строк — это не архитектура
В одном классе: OAuth, loopback-сервер, обмен токена, Web API, очередь, shuffle/repeat, навигация, все экраны, обработка ошибок и polling. Нет:
- ViewModel (зависимость lifecycle-viewmodel-compose подключена, но не используется);
- репозиториев;
- DI;
- навигации (ручные when/флаги);
- rememberSaveable;
- разделения UI и бизнес-логики.
Следствия: поворот экрана и process death убивают всё состояние (очередь, текущий трек, позицию, открытый экран); тестировать нечего; любой баг чинить страшно.
2.2. Gapless/crossfade не используются, хотя нативный API уже есть
В swiftify_core.h есть swiftify_core_preload_track, swiftify_core_crossfade_track, swiftify_core_completion_fd, swiftify_core_take_connect_events, swiftify_core_skip_remote. Kotlin-код не вызывает ни один из них (кроме take_end_of_track). Вместо этого:
- каждая смена трека — отдельный play_track;
- конец трека определяется опросом takeEndOfTrack() раз в 250 мс;
- кроссфейда нет вообще.
Результат: слышимый разрыв на каждом переходе, до 250 мс задержки плюс время буферизации. Это не «порт десктопа», это ручная имитация очереди поверх API, который специально сделан для бесшовного воспроизведения. Один из самых обидных выводов ревью: самая ценная часть кора не задействована.
2.3. Polling каждые 250 мс на главном потоке
MainActivity.kt:357-388: while (isActive) { pollCompletions(); playbackPositionMs(); currentTrackJson(); JSONObject(...); ... delay(250) } в Dispatchers.Main.
- JNA-вызовы синхронные и могут блокировать main thread.
- JSON текущего трека парсится 4 раза в секунду.
- progressMs меняется 4 раза в секунду → перекомпоновка плеера 4 раза в секунду.
- Это прямо противоречит правилу проекта «no polling», которое зафиксировано в документации.
Нужно: события из кора через fd/callback, обновление позиции раз в секунду (или только когда экран видим), withContext(Dispatchers.IO) для JNA, Lifecycle.repeatOnLifecycle.
2.4. PlaybackService — фиктивный foreground-сервис
Разбор PlaybackService.kt:
- onSkipToNext и onSkipToPrevious — пустые заглушки с комментарием «Handled in MainActivity or via broadcast». Никакого broadcast нет. Кнопки next/prev на локскрине, в шторке и на Bluetooth не работают, хотя PlaybackStateCompat их рекламирует.
- Нет MediaMetadata → локскрин не показывает название, артиста, обложку, длительность; seekbar в системном UI не работает.
- Нет MediaButtonReceiver → аппаратные/Bluetooth-кнопки не обрабатываются.
- Нет audio focus (AudioManager.requestAudioFocus) и ACTION_AUDIO_BECOMING_NOISY → музыка не глушится при звонке и продолжает играть в динамик при выдёргивании наушников.
- WAKE_LOCK объявлен в манифесте, но нигде не приобретается → при выключении экрана воспроизведение может остановиться.
- POST_NOTIFICATIONS объявлен, но runtime-запрос не делается → на Android 13+ уведомление не показывается, управление теряется.
- START_STICKY + onStartCommand без обработки intent == null: после перезапуска процесса сервис не вызывает startForeground() и система убивает его с RemoteServiceException.
- setOngoing(isPlaying) — при паузе уведомление можно свайпнуть, но сервис остаётся.
- Маленькая иконка — android.R.drawable.ic_media_play (платформенная, не monochrome) → на части устройств белый квадрат.
- Нет MediaBrowserServiceCompat/Media3 → Android Auto, Wear OS и нормальная интеграция с системой невозможны в принципе.
Правильный путь — Media3 MediaSessionService + ExoPlayer/кастомный Player поверх кора, а не самодельный сервис с Intent-экшенами.
2.5. Логика очереди сломана
- stopAtEndOfQueue выставляется в true только для альбома (MainActivity.kt:955) и никогда не сбрасывается. После одного альбома все последующие очереди будут останавливаться в конце.
- При repeatMode == 0 (repeat off) очередь всё равно переходит на трек 0 (MainActivity.kt:602-606). «Повтор выключен» и «повтор всей очереди» — одно и то же.
- prevTrack при позиции > 3 с делает seek(0), иначе уходит на предыдущий трек — это нормально, но при repeat-one всегда seek(0), что ломает ожидаемое поведение.
- «Custom play-next queue» из roadmap не реализован: очередь — это просто List<TrackItem> с индексом.
- Перестановки, удаления и «играть следующим» нет.
2.6. Spotify Connect
- Устройство всегда представляется как "Nothing Phone (1)" (SpotifyBridge.kt:99, :164, SettingsScreen.kt:181) — у всех пользователей одинаковое имя.
- В качестве device ID используется имя, а не стабильный уникальный идентификатор → два телефона конфликтуют, ID меняется при смене имени.
- Настройка не персистится (см. 1.5).
- Состояние connectEnabled не синхронизируется с реальным состоянием кора.
3. P1 — корректность данных и Web API
3.1. Экран плейлиста «лайкает» все треки
PlaylistDetailScreen.kt:85-89 и :142-146:
val likedUris = loaded.map { it.uri }.filter { it.isNotEmpty() }.toSet()
val currentSet = prefs.getStringSet("saved_track_uris", emptySet()).toMutableSet()
currentSet.addAll(likedUris)
prefs.edit().putStringSet("saved_track_uris", currentSet).apply()
При открытии любого плейлиста все его треки помечаются как лайкнутые в локальном хранилище. Дальше это используется как источник истины для кнопки «нравится». То есть:
- UI врёт;
- состояние лайков портится безвозвратно;
- реальная синхронизация с Spotify не делается (и не может из-за скоупов).
Правильно: отдельный запрос me/tracks/contains пачками по 50 ID, кэш с TTL, optimistic update только для конкретного трека, откат при ошибке.
3.2. Фолбэки показывают чужой контент
При ошибке загрузки плейлиста/альбома код подставляет recently played или другой список из tracks. Пользователь открывает «Мой плейлист», видит чужие треки и не понимает, что произошла ошибка. Это хуже пустого экрана. Нужны явные состояния Loading / Empty / Error(retry).
3.3. Нет таймаутов и внятных ошибок
HttpURLConnection без connectTimeout/readTimeout, inputStream читается без проверки responseCode, тела ошибок не читаются, соединения не закрываются в finally. При плохой сети запрос может висеть бесконечно, а пользователь — вечно смотреть спиннер.
В нативном мосте то же самое: если колбэк не вызван (кор не инициализирован, ошибка в Rust), isLoading остаётся true навсегда. Нет request-id -> отмены, нет таймаута на стороне Kotlin.
3.4. Поиск
- Вкладка «Playlists» есть, но searchResultsPlaylists никогда не заполняется (SearchScreen.kt:79,90 и всё). В search.rs есть только search_tracks_json и search_artists_json, метода для плейлистов нет. Кнопка мертва.
- Гонка результатов: при быстром вводе старый ответ может перезаписать новый; нет проверки, что ответ соответствует текущему запросу.
- Жанровые карточки — просто подставляют название жанра в поиск, никакого browse/categories API.
- Поиск артистов строится из результатов треков, а не из полноценного artist search.
- В search.rs запрос кодируется как trimmed.replace(' ', "+") и вставляется в spotify:search:.... Это не URL- и не URI-encoding: &, #, %, кириллица и emoji могут ломать запрос. Нужен нормальный percent-encoding.
3.5. Альбом открывается поиском по названию
openAlbumByTrack (MainActivity.kt:682-707) при клике на обложку ищет треки по названию альбома и берёт первый попавшийся album.uri. Если альбомов с таким названием несколько (переиздания, синглы, сборники) — откроется не тот. В метаданных трека уже есть album URI; нужно прокидывать его, а не реконструировать поиском.
Аналогично artist URI теряется: артисты хранятся как одна строка через joinToString(", "), а openArtistScreen(currentTrack.artist, "") ищет по имени. Несколько артистов, одноимённые артисты, фиты — всё ломается.
3.6. Пагинация и N+1
- collection_tracks_json и загрузка плейлиста тянут все треки без постраничности (лимит Spotify — 50/100 на страницу). Большие библиотеки не загрузятся или загрузятся частично.
- user_playlists_json делает последовательные запросы по каждому плейлисту (N+1) до 100 штук — это десятки секунд и риск rate limit.
- picture_size.first() берётся без выбора подходящего размера и без mosaic-обработки для плейлистов из нескольких обложек.
3.7. Прочая мелочь, которая ломает доверие
- На главной жёстко зашито «3,495 favourited tracks» (MainActivity.kt:1414, :1434) — число-заглушка.
- «Nothing Phone (1)», «snd_device 2», «API 34», «Android 14» — захардкоженная информация об устройстве в настройках.
- Примерные артисты/треки в UI.
- Нет logout и смены аккаунта.
- Нет обработки «нет сети», «нет устройства», «премиум не активен».
4. P1 — Rust-кор и лицензии
Изменения в spotify-core большие и все не закоммичены (M + untracked album.rs, search.rs). Это отдельный риск: если ноутбук умрёт, работа пропадёт.
Конкретно:
- В vendored librespot-core жёстко зашита страна "UA" (session.rs:402, :582). Это хак, который меняет каталог/доступность контента для всех пользователей и ломает его за пределами Украины. Должна быть настройка или реальный код страны, а не константа.
- В vendored Cargo.toml включён default = ["rustls-tls-webpki-roots"] — изменение поведения зависимости без объяснения.
- Условный спуфинг ОС под Linux на Android (session.rs) — потенциальное нарушение ToS Spotify и источник нестабильности; как минимум должен быть задокументирован и выключаем.
- В artist.rs удалены все тесты (#[cfg(test)] mod tests вырезан полностью). Это регресс, а не рефакторинг.
- Новые album.rs и search.rs не имеют полного GPL-заголовка с copyright, в отличие от остальных файлов. Для GPL-проекта это юридическая неаккуратность.
- Cargo.lock изменён на 442 строки — обновление зависимостей не проверено и не описано.
- build_so.sh и test_ndk.sh содержат абсолютные пути /home/heyily, собраны вручную, не интегрированы в Gradle.
5. P2 — сборка, репозиторий, поставка
Это, возможно, самый большой процессный провал.
5.1. android-app/ вообще не в git
git status показывает ?? android-app/ — весь порт не отслеживается. Внутри:
- нет .gitignore;
- local.properties с абсолютным путём к SDK;
- gradle.properties с org.gradle.java.home=/home/heyily/.jdks/jdk-17;
- нет Gradle wrapper (gradlew, gradle/wrapper/*);
- нет CI.
То есть проект не соберётся ни у кого, кроме автора, и любая ошибка не откатывается. Это нужно исправить до любого дальнейшего кода.
5.2. Устаревший тулчейн
- AGP 8.3.1, Kotlin 1.9.22, Compose BOM 2024.02.00, compileSdk/targetSdk 34 — на 2026 год это глубоко устаревший стек.
- targetSdk 34 не проходит требования Google Play (нужен 35+, дальше 36). Опубликовать приложение в текущем виде нельзя.
- enableJetifier=true — лишняя замедляющая настройка.
- settings.gradle на Groovy, build.gradle.kts на Kotlin DSL — несогласованно.
- В settings.gradle первыми идут Aliyun-мирror'ы — для глобального FOSS-проекта это сомнительная цепочка поставок; как минимум должно быть опционально и задокументировано.
- Нет signingConfig, isMinifyEnabled, proguard-rules.pro, bundle-конфигурации. Release-сборка не готова.
- Нет version catalog, нет dependency verification.
5.3. Нативная библиотека
- libspotify_core.so лежит готовым бинарником в jniLibs, Gradle его не собирает. Воспроизводимой сборки нет.
- Только arm64-v8a — эмулятор x86_64 и старые устройства не работают.
- .so не stripped, 15 MB; debug APK ~39 MB. Release-размер неизвестен, потому что release-конфигурации нет.
- NDK r26d. Для 16 KB alignment всё ок, но при переходе на targetSdk 35+ это нужно закрепить в CI-проверке.
5.4. Нет тестов, линта и CI
- Ни одного unit-теста, instrumentation-теста, UI-теста.
- Нет ktlint/detekt.
- 14 предупреждений компилятора никем не разбираются.
- lintDebug офлайн не запускается из-за отсутствующей в кэше зависимости; в CI его нет вовсе.
- Нет Android CI-workflow (в отличие от десктопной части).
6. P2 — UX, i18n, доступность, дизайн
- Нет strings.xml вообще. В res/ только ic_launcher.xml. Все строки захардкожены по-английски, хотя десктоп поддерживает русский. Для русского пользователя это сразу «чужое» приложение.
- Нет локализации чисел/дат/плейлистов.
- Нет светлой темы, нет dynamic color (Material You), все цвета захардкожены (Color(0xFF13100E) и т.п.).
- Иконки — эмодзи (🎵, 🎧, 🔥) в жанрах; в остальном платформенные android.R.drawable. Выглядит как макет.
- Доступность: нет contentDescription у большинства кликабельных обложек и кнопок, нет semantic-ролей, мелкие тач-таргеты, контраст текста Color(0xFF9E948E) на тёмном фоне ниже AA.
- Нет landscape/tablet-раскладок; на планшете всё растягивается в одну колонку.
- Нет edge-to-edge/insets-политики: платформенная тема Theme.Material.NoActionBar + ручные отступы → риск наезда на статус-бар/вырез.
- Нет splash screen, нет нормальной иконки (векторная заглушка).
- Нет пустых состояний, скелетонов, retry-кнопок, Snackbar для ошибок.
- Нет haptics, анимаций переходов между экранами (только внутренние).
- Тексты вроде «Favourited: 3495» и «Broadcast Nothing Phone (1) as speaker» выглядят как тестовый стенд.
7. Чего нет из десктопа
Если это действительно «порт», то список недостающего огромен:

- офлайн-загрузки и локальные файлы;
- статистика прослушиваний;

- Android Auto, Chromecast, Wear OS;

9. Итог
Как прототип — это живо и местами талантливо. Как порт — нет: самая сильная часть десктопа (нативный gapless/crossfade/DSP-кор) не подключена, а мобильная обвязка построена вокруг одного Activity и самодельного сервиса.
Как продукт — пока нет: вход ломается на скоупах и повороте экрана, через час отваливается токен, лайки врут, поиск плейлистов мёртв, настройки не применяются, репозиторий не отслеживается, release-сборки не существует.
Хорошая новость: почти всё это — не «переписать с нуля», а последовательно закрыть P0/P1. Нативный API уже готов лучше, чем его использует Android-слой; если начать с OAuth + Media3 + отказа от polling и ручной очереди, приложение за пару итераций станет принципиально другим.
